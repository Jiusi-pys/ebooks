# 服务器后端逐步替换计划（2026-10-05）

用户要求开始把生产后端逐步从 Node 替换为 Rust；保持现有界面、客户端接口、
书库数据、认证和 MCP 连接可用。团队规模最多 10 人，不引入集群调度或多主写入。
实施基线为 base a040ed4584f043ef521c7cb3444eb17c639087e6。

## 阶段和验收门槛

1. 在生产服务器部署独立 Rust 只读候选，绑定回环地址、独立工作区和独立密钥。
   全路由写入栅栏拒绝业务 mutation；同步仅接收入站数据，禁止 push 和文件上传，
   停止 WebHook 投递。MCP 六个只读工具可用于比较。Node 保持生产唯一写入者。
   以先失败测试验证栅栏、入站同步及重开，再构建 Linux 二进制并部署验收。
2. 保留 MySQL 生产账本，先盘点和冻结浏览器 session、账户加密、密码哈希、
   OAuth 状态、机器密钥、library/v1/v2、AI/tRPC 的外部契约。存储最终形态待用户
   回答；选择 SQLite 时增加独立数据转换及切换方案，选择 MySQL 时实现 Rust
   MySQL 仓库适配。第一阶段只读候选不决定最终存储形态。
3. 逐模块执行差分测试和真实 HTTPS 验收，补齐 Rust 浏览器登录/账户/AI 和
   library API。保持混合版本读取、原 operation ID、墓碑、同步世代和原文件哈希。
   任何数据结构改变先设计追加迁移、完整历史归档、旧版本起点和失败恢复。
4. 冻结旧写入者，取得 MySQL、原文件、OAuth、账户、配置和独立密钥共同时间点
   备份并复制到异机。最终转换到独立目标库，验证所有业务路由、原文件及
   session/OAuth 交接后，再切换 Nginx 和写入权。首次 Rust 写入之后，回退必须
   转移或恢复新增数据；禁止直接启动停写时刻的旧 Node 数据副本。
5. 验证正常/失败登录、写入与重复请求、两节点双向同步、重启、整库和单条版本
   恢复/手动删除、恢复后的世代更新/单写入者切换；观察期间保留旧镜像和备份。

## 方案审核

风险 Tier 3：涉及账户、密钥和生产数据写入权。用户已授权开始替换；各阶段仍以
实际门槛约束自动执行。独立维护者应审核最终写入切换的证据，当前没有独立审核结论。

理解检查：现有 Rust Host 绑定 CoreSession<SqliteRepository>，并非现有 MySQL
适配器；Node 浏览器会话不是 Rust owner token。直接替换 3000 端口会丢失登录、
账户及部分 AI/tRPC 行为，不能据已有 v1/v2/MCP 测试推断整体兼容。

反例检查：候选必须拒绝未知 mutation 路由、同步 push、文件上传、OAuth 状态
创建及定时 WebHook 出站。同步快照创建是上游控制面动作；候选不得向上游写入
业务操作。候选本地接收数据不等于获得生产写入权。

验证检查：第一阶段不改 schema；测试先固定候选写入栅栏与只入站复制行为，再
检查实际 Linux 构建、进程状态、回环 HTTP、原操作数量和文件哈希。完成第一阶段
仅表示生产服务器有可验收 Rust 候选，不能宣称 Node 已完全替换。
