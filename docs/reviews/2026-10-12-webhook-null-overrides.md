# Webhook 轮询后 Mirror 事件失败

整合发布检查在隔离 MySQL 8.4 与真实 Linux 服务上运行 55 项测试，首次得到
52 通过、3 失败；失败均是合法 Mirror 笔记事件返回 `invalid_webhooks`。
生产服务未参与这些测试。

## 根因和修复

`webhooks::tick` 通过可变 JSON 下标访问缺失的 `overrides`，会插入 `null`，
并在保存游标时持久化。`override_commit_source` 只初始化不存在的字段，遇到
这个 `null` 就拒绝后续合法事件。结果依赖后台轮询与请求的先后顺序。

现在轮询用 `get_mut` 查询，不创建缺失字段；提交事件时把缺失或 `null` 的
映射视为空映射。字符串等其他错误类型仍拒绝，不静默覆盖损坏状态。

没有新增字段、schema、迁移或回填；`overrides` 本来就是可选的对象字段。
兼容已有缺失、空对象和旧轮询生成的 `null`。旧程序回退仍可能重现原缺陷，
程序回退不能当作数据恢复。

## TDD 证据

- 新增确定性回归：创建笔记、运行一次轮询、关闭重开书库、提交 Mirror 事件。
  旧实现失败：HTTP 400 `invalid_webhooks`，预期 200（测试退出码 101）。
- 同一回归也覆盖已有 `null` 状态，轮询后精确重放仍只提交一次。
- 新增错误状态回归：字符串映射必须返回 400，不能创建笔记。
- 修复后 Windows `legacy` 11 项和 `webhooks` 3 项全部通过。
- Linux 完整测试、隔离 MySQL 整组重跑及精确提交的 GitHub 检查作为发布门槛。
  原始日志在本地 `.tools/main-release-20261012/`，发布结果以 PR 和部署回执为准。

同轮修复了 Windows CI 环境漂移：默认镜像为 VS 2026，而原生解析器构建脚本
明确要求 VS 2022；固定到 `windows-2022`，保留检查名称和全部测试步骤。

随后 Windows 策略检查暴露部署任务的时钟精度问题：快速创建的任务可能具有相同
`createdAt`，重启后选错最近任务，导致成功任务被重复部署。新增固定及回退时钟
回归，在原实现中两种情况均失败。现在用上一任务时间的下一个可表示浮点数作为
新任务时间下限，仍使用既有 JSON 数字格式；不改任务文件结构或历史记录。
部署测试共 16 项通过，覆盖持久化重开、最近任务查询及重复请求去重。

Linux 完整工作区测试最终为 206 通过、20 项按原有外部环境要求忽略；修复后隔离
MySQL 八个文件的 55 项全部通过，包括旧 Hono/MySQL 与真实原生服务差分、
old_v2 原文件交换和迁移夹具。

Windows 原生解析器与 WinUI 编译通过后，独立进程验收暴露陈旧断言：仍要求
6 个 MCP 工具，而共享核心既有契约已经是 85 个。使用当前源码编译的 Windows
服务复现此失败，更新验收为严格 85 个、名称唯一、保留原六项，并要求 HTTP 与
stdio 完整目录相同；独立进程、鉴权、OAuth、共享书库及关闭流程全部通过。
